# Pstack build and verification fit for Atlas

## Which TDD and TypeScript methods should Atlas retain?

### Takeaway

Use Pstack's focused regression workflow as the default for an ordinary bug with a cheap existing observable test; retain Matt's method for deliberate feature TDD, agreed public Test Seams, and integration-test design. These are useful routed methods, not two documents to concatenate. Retain the `atlas-implement` grouping only if its actual method selection and conflict rulings earn the wrapper. This is a source-contract and workflow-fit recommendation, not measured evidence that one prompt makes a model more effective.

Concrete TDD rulings that would justify composition:

1. **Route from user intent and scope.** Explicit feature TDD, red/green interface work, or requested integration-test design uses Matt. A bug with an obvious existing, observable, inexpensive check uses Pstack's focused regression loop. Explicit method choice wins. If both apply, select one loop and reuse the other's compatible test-quality guidance, rather than running two loops.
2. **Honor approved scope before the cheap-test escape.** An agreed integration Test Seam is intentional work, even when more expensive than a unit test. Pstack's general avoidance of expensive/integration-heavy setup must not silently downgrade that contract. If the agreed seam is unusable, expose the concrete gap and nearest useful proof.
3. **Resolve genuine seam ceremony, not imagined conflict.** Existing authorized regression tests already specify an observable boundary in many bug requests. Avoid asking the user to reapprove that same boundary. Missing or materially disputed feature interfaces still use the Matt/Atlas seam discussion. This is a proposed clarification to current governance, not already implemented.
4. **Keep evidence proportional.** A failing regression and passing run can satisfy both bug and TDD evidence; no mandatory PE report, second adversarial pass, browser recording, or Tracking artifact is needed unless selected for a material uncertainty or requested deliverable.
5. **Preserve optionality.** If Atlas elects to carry only one public TDD package, keep Matt's current adaptation as the broader method and borrow Pstack's focused practicality/evidence rules with provenance. That alternative needs a specific ruling because indiscriminately granting the escape changes seam commitments. Dropping Matt entirely would lose feature-interface testing guidance and support examples.

### Gaps

- No comparative model trial, bug corpus, cost measurement, or adherence evaluation was run. Source concision and good prose are not evidence of model success rates. Default-fit recommendations are judgments from contracts and workflow burden.
- No TypeScript compiler trial of the examples was performed. The negative-duration observation follows directly from the declared plain numeric field; exact behavior under each project's compiler options remains to be checked before packaging.
- The two sources' human seam policies do not establish whether Leonardo wants the same confirmation boundary for every future bug task. The proposed routing must be ratified as an Atlas rule if adopted.

## Which impact and adversarial review methods complement Atlas Review?

### Takeaway

Keep `blast-radius` and `interrogate` as original-name optional methods, with portability and authorization patches. Neither replaces Atlas Review's Standards/Spec split, PE Verify's behavior proof, or independent Doubt-Driven Development's in-flight challenge. Do not make either another mandatory Tracking gate or automatic rerun.

### Cited Findings

- **`blast-radius` purpose and direct scope.** Its only own file is a 50-line entry: trace non-obvious consumers, library source/pins/patches, wire/storage contracts, flags, timing, and downstream execution; find the one or two facts safety depends on; prove them by running real code; distinguish risks checked and cleared. Its evidence ladder runs from unsupported assertion through source citation and failure-path tracing to executable checks and real-app reproduction, with explicit reporting of where proof stopped. [Blast radius][P-BLAST], lines 13-46. Local: `/private/tmp/atlas-pstack-analysis-20261015/skills/blast-radius/SKILL.md:13-50`.
- **Blast closure is conditional, not a reason to import all Pstack orchestration.** `how` is a companion explanation; `why` step 2 supplies Git/PR history anchoring; large changes can call `arena`; output calls `unslop`. `how` includes explorer/explainer templates; `why` includes epistemics, investigator/synthesizer templates, a source-playbook index, and seven source-category playbooks plus incident context. Arena calls the separate-state, laziness, first-principles redesign, and prove-it-works principles; the last points to show-me-your-work for large auditable artifacts. [Blast references][P-BLAST], [how][P-HOW], [why][P-WHY], [arena][P-ARENA], [unslop][P-UNSLOP], [prove-it-works][P-PROVE]. This is the traced reference closure, not a recommendation to execute/import each linked workflow for a small impact check.
- **Tool/model assumptions in that closure.** `why`'s code anchor runs Git/blame/log and `gh pr view`; full `why` broadly searches available source control, tickets, docs, chat, infrastructure, errors, and analytics. Its agents are write-capable solely to retain MCP access, while instructed not to write. `how`, `why`, and arena refer to Pstack settings, default Claude/Grok slugs and Cursor-style Task parameters, with other-harness mappings and sequential role fallback. Arena produces parallel candidate artifacts and grafts a result; it is a much larger activity than a targeted impact test. [why lines 11-56][P-WHY], [how lines 11-30][P-HOW], [arena lines 17-44][P-ARENA].
- **`interrogate` purpose and complete support scope.** It launches one reviewer per configured model against the same intent, diff/files, rubric, and code-quality lens; synthesizes overlap/disagreement; applies lead judgment; returns Act On / Consider / Noted / Dismissed plus agreement map. Its four support files are `reviewer-prompt.md`, `rubric.md`, `code-quality-review.md`, and `lead-judgment.md`. The entry explicitly says **do not auto-apply changes**; the reviewer template permits no findings. [Interrogate][P-INT], [template][P-IP], [rubric][P-IR], [quality lens][P-IQ], [lead judgment][P-IL]. Local root: `/private/tmp/atlas-pstack-analysis-20261015/skills/interrogate/`.
- **Interrogate's model diversity is a claim, not measured efficacy.** The source says diversity supplies the adversarial signal, defaults to `claude-opus-5-5-xhigh` and `grok-4.7-xhigh-fast`, reads `~/.cursor/rules/pstack-models.mdc` or `~/.agents/pstack-models.md`, falls back after slug rejection, and can run roles itself sequentially when no subagents exist. Sequential self-review does not establish independent context or model diversity, and model agreement does not prove a finding. [Interrogate lines 9,27-44][P-INT].
- **Interrogate contains an important internal tension.** Its quality lens makes crossing 1,000 lines a presumptive blocker and favors ambitious structural simplification; its lead judgment rejects premature abstractions, preference-only findings and out-of-scope changes, and says a long Act On list may reflect weak filtering. The lead framework is a valuable safeguard; neither five actionable findings nor 1,000 lines should become a universal correctness threshold. [quality lens lines 21-43][P-IQ], [lead judgment lines 18-58][P-IL].
- **Atlas Code's actual method differs.** It pins branch/commit/working-tree scope including untracked content; separately reviews Standards and originating Spec in fresh contexts; gives documented repo standards precedence over labeled smell heuristics; checks ticket/evidence claims; deliberately **does not merge or rerank the axes**. Review is read-only toward product code, with explicit permission needed for fixes. Static mode runs existing scoped lint/typecheck and judges findings without fixing. [Code review][A-CODE], lines 16-46,63-96; [Review ownership][A-OWN], lines 5-11; [Review spine][A-REVIEW], lines 21-23; [Static][A-STATIC].
- **Independent Doubt-Driven is a different timing and context contract.** Addy's pinned source matches the installed independent skill byte-for-byte. It challenges in-flight non-trivial decisions with artifact + contract, excludes the author's reasoning/CLAIM from the reviewer prompt, reconciles findings and bounds cycles at three. It treats TDD RED as the doubt step for behavioral claims. Interactive cross-model CLI escalation is offered and separately authorized each time; non-interactive runs skip it explicitly. Nested orchestration has explicit limitations. [Doubt-Driven][D-DDD], lines 42-47,75-166,181-189,223-243; [orchestration constraints][D-ORCH], lines 302-339. Local: `/private/tmp/atlas-implement-addy-20261014/skills/doubt-driven-development/SKILL.md`.
- **Team Up owns portable delegation choices, not a particular provider roster.** It selects available models/efforts deliberately, respects fixed custom roles, uses the smallest capable team, and treats its ladder as a heuristic without measured equivalent budgets or success guarantees. Concrete Review/Tracking integration:

- A review request with uncertain downstream effects can use `blast-radius` for that identified risk. Return the proof, command, scope/revision and unproven assumptions to the owning Code report; a scratch probe does not authorize product fixes or broad harness construction.
- Explicit `interrogate` is an alternative/additional review method, not the automatic Code gate. If composing it into `atlas-review` later, define it as a separate mode with separate output; do not mix its consensus ranking into the existing Standards/Spec axes. That would be genuine mode routing worthy of an Atlas wrapper, but is unnecessary to ship the original-name package.
- Team Up can retain actual different providers when available; repeating one available model in isolated contexts must be labeled same-model independent review, and sequential self-review must be labeled degraded. No automatic external CLI or PR fallback is needed to finish a read-only review.
- A shared evidence receipt can satisfy multiple selected disciplines. Do not append mandatory Interrogate, blast-radius, or Doubt reruns to Tracking's existing single automatic Code review. Record selected findings and resolutions in existing Execution Evidence / Complete Review Record, retaining user acceptance.

### Gaps

- The source provides no controlled evidence that Claude/Grok diversity beats two independent same-model contexts, Atlas's two-axis method, or a single well-scoped reviewer. The quality of the lead filtering framework is not evidence that its models achieve higher precision.
- Provider defaults and model-name fallbacks were not invoked. The current task harness advertises GPT models, so cross-provider behavior is unavailable here; this does not establish what another Atlas installation supports.
- This research did not run probes against a changed application, open PRs, install settings, or test external subprocess credentials. No concrete bug discovery or runtime-review efficacy is claimed.

## How should generation, maintenance and benchmark checks interact with PE Verify?

### Takeaway

Keep `create-verification-skill`, `maintain-verification-skill`, and `benchmark-checklist` as original-name complements with narrowly scoped patches. The generator creates and proves project-specific driving knowledge; maintenance keeps that knowledge current; the checklist validates performance claims; PE Verify runs selected checks and renders a report. Their complementarity strengthens the case for restoring the original `pe-verify` package name rather than creating a larger `atlas-verify` composition.

It recognizes `.cursor`, `.claude`, `.pi`, and `.agents` project skill locations rather than requiring AFK. 1. A project-local `verify-<app>` skill supplies launch, isolation, stable selectors/commands, doctor, feature journeys, cleanup and evidence paths. It can execute alone. Its maintained map is the source for how to drive the app, not evidence a run passed.
2. When PE Verify is selected, read that local recipe as execution knowledge. Scope selected features/entrypoints explicitly, record checked revision and real actions, and produce PE's report once. Do not add a second “generator proof report” for the same run. Generating a new skill still requires its own first-run proof; PE output is optional packaging of that proof.
3. Do not pass a feature-map directory verbatim through PE's loose Markdown QA-list parser: headings such as `Gotchas` and nested entrypoint bullets are not independently intended QA items. Explicitly derive item IDs from feature/subfeature IDs and record selected entrypoint coverage in summary/checkpoints/evidence. Keep the map as authoritative driving knowledge and the selected QA list/report as run scope.
4. Translate lifecycle and coverage statuses honestly: maintenance `clean/changed/blocked` is not a PE item verdict; `verified-unreachable` is a concrete attempted path plus unmet prerequisite, normally `skipped` when behavior could not be checked, not `pass`. Unselected entries in selective reports are `not-run`; unavailable environments are `skipped`. One proof through a convenient entrypoint does not verify other entrypoints.
5. Preserve PE schema v1 unless a real cross-surface report requirement warrants a versioned change. Browser recordings/checkpoints/screenshots map naturally. CLI/service assertions can use code checks and commands/transcript paths in evidence. Native desktop/video or rich transcript presentation is not supplied merely by relabeling it browser. Unknown extra fields cannot be added to schema v1. Store cited evidence/media within the run layout when producing PE reports so cleanup retains it and media paths validate.
6. Run `benchmark-checklist` only for an actual performance claim. Reuse its measurement receipt in a code/mixed item or linked detailed artifact, with raw repetitions/ranges/errors/work counts retained. PE report validation proves JSON/media integrity, not benchmark validity. Neither benchmark nor PE success means shipped, released, or accepted.
7. Tracking links the selected report/receipts and unresolved gaps once. It retains its existing Code review and acceptance policy. Generation maintenance, benchmark repetition, multimodel Interrogate and impact probes are not additional unconditional gates. No AFK installation is needed to perform any of this.

Actionable priorities:

- **First:** ratify TDD route/precedence and original-name PE policy. Prototype the method selector wording against four cases: cheap bug regression, explicit feature TDD with approved seam, requested integration test requiring setup, and no meaningful executable seam. Success means correct route, proportional proof and no duplicate confirmation/gates.
- **Next:** prepare native-name packaging candidates for `benchmark-checklist`, generator + maintenance, and `blast-radius`; keep all companion loads self-contained or explicitly declared without AFK. Patch only identified capability/authorization/contract issues.
- **Then:** trial `interrogate` on a known diff using actual available reviewers, score findings against known outcomes, and record whether model diversity actually happened. Preserve Standards/Spec gate outputs separately.
- **Before TypeScript adoption:** repair or remove overclaiming examples and universal mandates, then test examples under representative strict compiler options and existing repository conventions. Do not promote it into global policy on prose quality alone.
- **Before claiming integration works:** generate one real project-local verification skill, prove one feature and evidence survival, maintain all seeded features, and feed one selected run into unchanged PE schema/renderer. Use the resulting artifacts to decide whether any adapter deserves code or an Atlas composition. None of those trials was performed here.

### Gaps

- These notes establish source contracts and architectural compatibility, not observed runtime delivery. No skill was executed, installed, composed, renamed, pushed, committed or published; no product source was edited.
- PE report templates/scripts and source manifests were inspected; renderer/browser/media efficacy and native/CLI ergonomics were not tested. No full product GUI QA is claimed.
- Universal minimal sample count is not sufficient statistical guidance for every latency distribution or repeated paired workload; changing benchmark policy needs a deliberate Atlas ruling and a representative trial, not an arbitrary new number.
- No evidence establishes which current projects need a generated local skill enough to justify ongoing maintenance. Start with one actual difficult user path rather than generating maps across all repositories.
- Local mirrors provide immutable primary source content. These notes do not establish that the pinned commits are today's latest upstream or that any Pstack integration has already shipped.
