# Interrogate

Spawn one reviewer per configured model to adversarially review code changes. The adversarial signal comes from model diversity, not assigned personas. The deliverable is a synthesized verdict. Do NOT auto-apply changes.

## Step 1, Scope

Identify what to review from context:

- If the user points at specific files or a diff, use that.
- If on a feature branch, run `git diff main...HEAD` (or the appropriate base branch) for the full changeset.
- If the user's message references recent work, gather the relevant files.

Pin the requested base and checkpoint before dispatch. Include scoped uncommitted changes and additions when they belong to that checkpoint; exclude unrelated working-tree files. Package the diff or file contents with any surrounding context files the reviewers need to understand the code.

## Step 2, Intent

Before spawning reviewers, state the intent in one clear paragraph from the user's message, commit messages, the PR description if one exists, and the code. If you're unsure about the intent, ask the user before proceeding.

## Step 3, Spawn Reviewers

Choose reviewers using the host's available models and dispatch tools, honoring the user's reviewer choices and project policy. For a multimodel review, prefer at least two independently run models from different families when available. Supply each the same intent, diff and supporting context; keep reviewer contexts separate and product code read-only. Bound concurrency to the host's capacity.

State each actual model and whether the run has cross-family diversity, same-family diversity, same-model isolated contexts, or sequential self-review. Separate contexts are not model diversity. If a requested model is unavailable, explain the gap and resolve the fallback with the user; do not silently substitute. Without explicit model requirements, use the available reviewers and disclose degraded independence. If the host cannot delegate, perform a sequential review and label that limitation.

Read `references/reviewer-prompt.md` and fill in the same template for every reviewer with the stated intent, the diff or file contents, the rubric from `references/rubric.md`, and the code-quality lens from `references/code-quality-review.md`.

## Step 4, Synthesize

As results come back, build a unified picture. Parse every reviewer's findings. Merge findings that describe the same issue differently, and note which models raised each one. Independent agreement is a useful signal, not proof. Verify material findings against the code and stated constraints, including findings raised by only one reviewer. Read a lone model's finding, but weight it accordingly. Note disagreements. If one model flags something and another explicitly says the opposite, that is context for the verdict.

## Step 5, Lead Judgment

You are the lead reviewer, a pragmatic senior engineer, not a neutral aggregator. Read `references/lead-judgment.md` for the full framework. Put every finding in one of four buckets, with the model(s) that raised it and a one-line rationale.

- **Act on**. Real issues affecting correctness, security, or maintainability given the actual goals. They would block a real PR.
- **Consider**. Legitimate, but you're not sure they outweigh the cost of addressing them now. Worth the user's attention.
- **Noted**. Technically valid but not actionable. Context-dependent, premature optimization, or low-impact at this stage.
- **Dismissed**. Wrong, nitpicky, or missing context, with a brief reason.

## Output Format

### Intent
> [The stated intent paragraph from Step 2]

### Reviewers
- Reviewer [label]: [actual model name], [N findings] (one bullet per reviewer)
- Diversity/independence: [actual model families, context isolation and any unavailable reviewers]

### Act On
[Each: description, which models raised it, why it matters.]

### Consider
[Each: description, which models raised it, the tradeoff.]

### Noted
[Brief list.]

### Dismissed
[Each with a brief rationale.]

### Agreement Map
[Where models agreed and diverged, and what that pattern tells us.]
