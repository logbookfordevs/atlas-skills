# Review obsolete installations

Establish why each candidate is obsolete using a previous manifest, installation receipt, source history or the user's identified cleanup scope. Verify its installed source, skill identity, actual path, target agents and project/global scope. If ownership or history is unclear, report it as an unclassified extra and retain it.

Before requesting approval, list the exact proposed removals, evidence that each is retired, replaced or duplicated, and any replacement already installed. Inspect shared copies and links to identify effects on other agents, projects or profiles. A skill that disappeared from the stack can still serve another workflow; disclose that use or uncertainty. Keep replacements and unrelated user files intact.

Ask the user to approve the named targets and scope. A general request to check or clean up is not approval of an unseen removal list. Reuse approval already given for those exact targets. If inspection changes the targets or effects, present the revised proposal before removing anything.

After approval, use the installed manager's supported, scoped removal command, consulting its help. Preserve shared copies still needed elsewhere; if a tool cannot express the approved scope safely, explain the limitation instead of broadening removal. Do not delete a repository, parent skill directory or user modifications as a shortcut. Distinguish removing availability links from deleting stored files.

Reinspect the intended scope after each removal. Report what was actually removed, what remains available, preserved shared copies and any failures or gaps. A proposed or attempted removal is not a completed cleanup.
